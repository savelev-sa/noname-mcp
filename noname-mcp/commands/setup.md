# /setup - onboarding

The plugin ships only a thin proxy. The MCP server is a separately-installed local service; the backup agent is a separate product. Get the user to a working state.

**Voice (important):** the user is a backup admin, not a developer. In everything you SAY, use plain language — "a quick one-time setup is needed", "installing…", "ready". Do NOT surface internals in the default narration: no endpoints/URLs, no JSON or field names, no `next_action`/`installer_url` tokens, no "MCP server"/"proxy"/"localhost:19360". The `noname_setup` result already carries a plain-language message (it names the backup product as this machine is configured to name it) and an `assistant_note` — relay those. The mechanics below are for YOU to execute, not to read aloud. Only expose technical detail if the user explicitly asks.

1. **Ask the proxy, not the shell.** If the full backup toolset is available, the server is up - call `get_agent_health` and skip to step 3. If only the `noname_setup` tool is exposed, call it: it returns ONE structured status `{server_installed, endpoint, installer_url, installer_url_configured, agent_installed, next_action}` - act on `next_action`. Do NOT probe via shell (curl /health, printenv, registry, Program Files) - the proxy already did all of that. Shell probing is the LAST-RESORT fallback ONLY when the proxy MCP itself failed to load (see the `onboarding` skill).
2. **Act on `next_action`:**
   - **`configure_installer_url`** - setup isn't configured on this computer yet. Say plainly: "A one-time setup is needed, but it hasn't been configured on this computer yet — please ask your administrator to finish it." (For the admin, if asked how: set the `NONAME_MCP_INSTALLER_URL` environment variable to the page or file serving the installer, then reload.) Do NOT attempt a download.
   - **`install_server`** - offer to install it (consent-gated):
   a. **Ask for explicit confirmation FIRST (mandatory), in plain language:** "Setting this up needs a one-time install on this computer. I can download it and run it now — it takes about a minute, and Windows will ask you to approve it. Go ahead?" It names BOTH verbs deliberately — consent to a download is not consent to running it — and warns about the Windows prompt before it appears. If the user declines -> tell them they can run the installer themselves, and **do not ask again**; re-asking treats "no" as "not yet". (Under the hood the source is the status's `installer_url`; don't say the URL unless asked.)
   b. **On consent, call `noname_install_server` with `confirmed: true`. Do NOT shell out to do this.** The tool fetches from the release the status names, verifies the published checksum BEFORE executing anything, runs the installer silently, and polls until the service answers. The shell version of these steps is the improvised flow this tool exists to replace: it cannot verify a checksum, so it runs an elevated installer on the strength of a URL alone.
   c. **Mechanics you are NOT to work around:** the silent switches suppress the installer's own dialogs, not the Windows approval prompt. That prompt is the one gate here that is not ours — never suppress, pre-empt or route around it. Say "installing…" while it runs.
   d. **Relay what the tool reports, and name the STATE it leaves the machine in** — the part failure text usually omits, and the part that decides whether the user's next move is right. Checksum mismatch: nothing was installed, nothing was executed, and it will not be — **never retry**, because a corrupted download and a substituted file look identical from here. Download failure: nothing changed. **Non-zero installer exit: it may be PARTLY installed** — say that outright, because "setup failed" implies the opposite and nobody hunts for a half-installed service they believe never existed; check Apps & Features and remove it there before a fresh attempt. Never healthy: it IS installed and not yet working.
      Once it responds, the proxy detects the server by itself (background re-probe) and refreshes the tools in the SAME session (`notifications/tools/list_changed`) — calling `noname_setup` again also triggers this. ONLY if the backup tools still do not appear (fallback): ask the user to **QUIT the app completely and reopen it**, and say plainly that closing the window is not enough on an app that keeps running in the tray or menu bar — they right-click its tray icon and choose Quit (Выход) first. "Restart" on its own is not a followable instruction there: the close button hides the window, the process lives on, nothing reloads, and the user is left believing the product is broken.
   e. **Manual fallback (always available):** the user can instead double-click the same downloaded installer.
   f. **Uninstall / repair (if needed):** run `unins000.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART` from the server's install directory (it is also registered in Apps & Features).
3. **Backup agent** - detect it (`get_agent_health` when the server is up, or the `agent_installed` field of the `noname_setup` status). If ABSENT, only show / open the official download link via `open_download_page` - NEVER silently install the agent.
   - Official agent download: https://www.msp360.com/backup/windows-backup-software/
4. **Finished setup is not a protected machine.** Once everything is up, say that setup is done and you can now manage their backups — **never that backups are working, protected or ready.** Nothing is protected until there is a destination and a plan, and "you're covered now" is the sentence a user stops checking after. Name what comes next in words, not command tokens: add a storage destination, create a backup plan, check status, restore.

Windows v1. The MCP-server installer may be run silently ONLY with the user's explicit consent (step 2a). The backup AGENT is never silently installed - detect + link only.
